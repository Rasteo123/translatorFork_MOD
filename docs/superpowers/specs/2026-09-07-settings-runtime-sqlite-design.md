# SQLite-хранилище изменяемого состояния API-ключей

Дата: 2026-09-07

## Контекст

`SettingsManager` сейчас хранит в одном JSON два разных класса данных:

- пользовательскую конфигурацию: API-ключи, провайдеры, тему, пути,
  параметры перевода и состояние интерфейса;
- конкурентное runtime-состояние ключей: историю запросов, время исчерпания
  квоты и уровень ограничения по каждой модели.

Из-за второго класса данных менеджер поддерживает RAM-кэш, disk baseline,
debounce, ручное объединение таймстампов и three-way merge между процессами.
Полная перезапись JSON остаётся неудобной единицей конкурентного изменения для
счётчиков и ограничений.

## Цель

Вынести только изменяемое состояние квот в SQLite, сохранив:

- `settings.json` как источник пользовательской конфигурации и списка ключей;
- существующий публичный интерфейс `SettingsManager`;
- существующую структуру `api_keys_with_status`, которую получают UI, CLI,
  переводчик, reader и QA;
- автоматическую совместимость с файлами настроек старого формата.

## Не входит в работу

- перенос всех настроек в SQLite;
- изменение формата API, которым пользуются потребители `SettingsManager`;
- добавление сторонней ORM или новой зависимости;
- перенос проектных кэшей `TranslationProjectManager`;
- переработка политики квот, времени сброса или событий интерфейса;
- хранение исходных API-ключей в новой базе.

## Выбранный подход

Новый `KeyRuntimeStore` будет внутренним компонентом `SettingsManager`.
Потребители продолжат вызывать `load_key_statuses()`, `get_key_info()`,
`increment_request_count()`, `mark_key_as_exhausted()` и остальные текущие
методы. Фасад будет объединять записи ключей из JSON с состоянием из SQLite.

Отдельный сервис с переписыванием всех потребителей отклонён из-за широкой
зоны изменений. Постоянная двойная запись JSON и SQLite отклонена, потому что
создаёт два источника истины.

## Компоненты

### `KeyRuntimeStore`

Новый модуль `gemini_translator/utils/key_runtime_store.py` отвечает только за:

- создание и обновление схемы;
- транзакционные чтения и изменения состояния ключа и модели;
- импорт legacy-состояния;
- очистку состояния удалённых ключей;
- проверку целостности и карантин повреждённой БД.

Компонент не знает о Qt, настройках провайдеров и правилах расчёта окна квоты.
Нужные timestamps и готовые значения статуса ему передаёт `SettingsManager`.

### `SettingsManager`

`SettingsManager` остаётся фасадом и отвечает за:

- ключи и провайдеры в JSON;
- вычисление reset policy;
- объединение JSON-конфигурации с runtime-состоянием при чтении;
- события Qt и отображаемые ошибки;
- удаление legacy runtime-полей из JSON после успешной миграции.

Three-way merge JSON сохраняется для обычных настроек и списка ключей.
`_merge_disk_timestamps()` удаляется после завершения миграции, потому что
SQLite становится единственным источником runtime-состояния.

## Путь к базе

Путь выводится из `config_file`:

```text
settings.json         -> settings.runtime.sqlite3
project_settings.json -> project_settings.runtime.sqlite3
```

База создаётся лениво: чтение обычных проектных настроек не должно оставлять
пустой SQLite-файл. Создание происходит только при наличии legacy-статусов или
при первом обращении к операциям состояния ключей.

## Идентификатор ключа

SQLite не хранит исходный API-ключ. `key_id` вычисляется как шестнадцатеричный
SHA-256 от UTF-8-представления ключа. API-ключи обладают достаточной энтропией,
поэтому идентификатор позволяет устойчиво связать JSON и SQLite, не создавая
ещё одну копию секрета на диске.

## Схема SQLite

```sql
CREATE TABLE runtime_meta (
    name TEXT PRIMARY KEY,
    value TEXT NOT NULL
);

CREATE TABLE key_model_status (
    key_id TEXT NOT NULL,
    model_id TEXT NOT NULL,
    exhausted_at REAL,
    exhausted_level INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (key_id, model_id)
);

CREATE TABLE key_requests (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    key_id TEXT NOT NULL,
    model_id TEXT NOT NULL,
    requested_at INTEGER NOT NULL
);

CREATE INDEX key_requests_lookup
    ON key_requests (key_id, model_id, requested_at, id);
```

Каждый запрос хранится отдельной строкой. Это сохраняет несколько запросов с
одинаковым секундным timestamp, которые текущая модель данных представляет
повторяющимися элементами списка.

Версия схемы хранится в `PRAGMA user_version`. В `runtime_meta` хранится
отметка завершённого импорта legacy JSON.

## Настройки соединения и транзакции

Каждая операция использует короткоживущее соединение стандартного `sqlite3`:

- `PRAGMA journal_mode=WAL` при инициализации;
- `PRAGMA busy_timeout=5000` для каждого соединения;
- `BEGIN IMMEDIATE` для read-modify-write;
- обычная транзакция для согласованных пакетных чтений.

Короткоживущие соединения не требуют `check_same_thread=False`, не связывают
жизненный цикл БД с QObject и безопасно работают из GUI- и worker-потоков.

После истечения `busy_timeout` ошибка возвращается вызывающему коду. Скрытого
повторного сохранения состояния в JSON не будет.

## Чтение

`load_key_statuses()`:

1. берёт из JSON копии записей с `key` и `provider`;
2. вычисляет `key_id` для каждого ключа;
3. одним запросом получает статусы и requests для набора идентификаторов;
4. собирает прежний `status_by_model`;
5. возвращает прежний список словарей.

`get_key_info()` использует тот же путь для одного ключа. Возвращаемые структуры
остаются независимыми копиями: изменение вызывающей стороной не меняет БД без
явного вызова метода сохранения.

`load_settings()` также материализует `api_keys_with_status` в возвращаемой
копии, чтобы сохранить текущий публичный контракт. Внутренний `_cache` и JSON
при этом содержат только конфигурационную часть. Симметрично `save_settings()`
отделяет переданные runtime-поля и направляет их в `KeyRuntimeStore`.

## Изменения состояния

- `increment_request_count()` добавляет одну строку `key_requests`, удаляет
  timestamps за пределами рассчитанного окна и возвращает новый count.
- `decrement_request_count()` удаляет ровно одну последнюю строку с порядком
  `requested_at DESC, id DESC`.
- `mark_key_as_exhausted()` делает upsert `exhausted_at` и уровня 2.
- `clear_key_exhaustion_status()` обнуляет exhaustion-поля, не затрагивая
  историю запросов.
- автоматическое обслуживание удаляет истёкшие requests и сбрасывает
  неактивные ограничения одной транзакцией.

Существующие сигналы и события отправляются после успешного commit, вне
транзакции.

## Изменения списка ключей

`save_key_statuses()` разделяет входную совместимую структуру:

- `key` и `provider` сохраняются в JSON;
- `status_by_model` сохраняется транзакцией в SQLite.

При добавлении ключа меняется только JSON. При удалении сначала атомарно
сохраняется новый список JSON, затем удаляются строки его `key_id` из SQLite.
Если второй шаг сорвётся, останется недоступный orphan без исходного секрета;
он не попадёт в чтение и будет удалён следующей уборкой.

## Миграция старого JSON

Миграция запускается, если JSON содержит `status_by_model` или старые поля
`requests`/`exhausted_at` на уровне ключа.

1. Существующая миграция старой формы нормализует данные в
   `status_by_model` в памяти.
2. `KeyRuntimeStore` начинает транзакцию, импортирует статусы и все requests,
   записывает отметку импорта и делает commit.
3. Только после успешного commit `SettingsManager` удаляет runtime-поля из
   JSON и сохраняет его штатным атомарным writer-ом.

Если очистка JSON не удалась, отметка в SQLite предотвращает повторный импорт
и дублирование requests. Следующее успешное сохранение настроек снова удалит
legacy-поля. Если транзакция SQLite не завершилась, JSON остаётся нетронутым.

## Ошибки и восстановление

При первой инициализации существующей БД в экземпляре store выполняется
`PRAGMA quick_check`. Карантин применяется только когда результат проверки
указывает на повреждение:

```text
settings.runtime.sqlite3.corrupt-YYYYMMDD-HHMMSS
```

После успешного карантина создаётся пустая БД, а `SettingsManager` публикует
событие `key_runtime_store_corrupted` с исходным и резервным путями. Ключи и
обычные настройки остаются в JSON.

Ошибки разрешений, занятости после timeout и записи не считаются повреждением:
файл не переименовывается, ошибка сохраняется в менеджере и публикуется как
`key_runtime_store_failed`. Мутация сообщает об ошибке вызывающему коду, а не
делает незаметный fallback в JSON.

## Совместимость

Публичные методы и форма данных сохраняются. В частности, без изменений
остаются потребители в UI, CLI, `translation_engine`, `gemini_reader_v3`, QA и
обработчиках API.

`load_settings()` сохраняет прежнюю объединённую форму, хотя рекомендуемым
путём для полного состояния ключей остаётся `load_key_statuses()`. AST-grep
используется для проверки всех прямых и косвенных потребителей перед удалением
legacy-полей из JSON.

## Проверка

Разработка идёт тестами от поведения к реализации.

### `KeyRuntimeStore`

- создание схемы и повторное открытие;
- отсутствие исходного API-ключа в файле БД;
- сохранение нескольких запросов с одинаковым timestamp;
- конкурентные increment из двух экземпляров без потерянных строк;
- decrement удаляет один последний запрос;
- независимость моделей одного ключа;
- атомарное обновление exhaustion-полей;
- очистка ключа и orphan-записей;
- `busy_timeout` и проброс ошибки;
- `quick_check`, карантин и повторное создание.

### Интеграция `SettingsManager`

- прежняя форма `load_key_statuses()` и `get_key_info()`;
- однократная миграция legacy JSON;
- отсутствие дублей после повторного запуска с неочищенным JSON;
- JSON очищается только после commit SQLite;
- `save_key_statuses()` корректно разделяет конфигурацию и runtime;
- два менеджера одновременно увеличивают счётчик без lost update;
- текущие reset policy и события сохраняются;
- удаление ключа не возвращает orphan-состояние.

AST-grep MCP используется для инвентаризации потребителей и финального
контроля, что runtime-поля больше не изменяются JSON-путями. После фокусных
тестов выполняется полный набор проекта.

## Разбиение реализации

1. Добавить и отдельно протестировать `KeyRuntimeStore`.
2. Добавить совместимую сборку статусов при чтении без удаления старого пути.
3. Перевести отдельные мутации на SQLite.
4. Добавить миграцию и очистку legacy-полей.
5. Удалить `_merge_disk_timestamps()` и недостижимую JSON-логику runtime.
6. Выполнить AST-grep-аудит потребителей и полный тестовый прогон.

Каждый шаг должен оставлять рабочую совместимую систему и завершаться
отдельным проверяемым коммитом либо быть объединён с соседним шагом только при
неразделимой миграции интерфейса.
